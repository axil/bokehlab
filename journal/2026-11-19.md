# 2026-11-19 — imshow view-range fix (0.3.1)

## Symptom

`imshow(a)` displayed only a thin strip of the image — the view range was calculated
incorrectly and most of the image was outside the visible frame. The workaround
`p = Figure(); imshow(a, p=p); p` in one cell worked, which pointed at the code path
where `imshow` creates its own figure.

## Root cause

For `flipud=False`, `imshow` created its figure with a **reversed y range**
(`y_range=[h+pad, -pad]`) and vertically flipped the image data (`np.flipud`) — a
workaround from the Bokeh 2 era (the original `y_range.flipped=True` approach was
already commented out as "does not work due to an issue in bokeh").

In Bokeh 3.10, BokehJS's `ImageBaseView._paint` mishandles a reversed source range:
with `y_range=[220, -20]` and the glyph anchored at `y=200`, the mapped screen
position came out as `sy=270.8, sdh=241.7` against a frame of `[5, 5, 300, 295]`, so
the paint transform placed the image at device y ∈ [270.8, 512.5] — everything below
y=295 (the frame bottom) was clipped, leaving only a ~24 px strip.

Reproduced with **raw Bokeh, no bokehlab involved** (`figure(y_range=[220, -20])` +
`image()` glyph), confirming it is a Bokeh 3.10 rendering bug, not a wrapper bug.
A default `p = Figure()` gets a `DataRange1d` that auto-fits to the glyph, so no
reversed range ever appears — which is why the workaround worked.

## Fix (`bokehlab/__init__.py`, `imshow`)

Replaced the reversed-range + `np.flipud` workaround with Bokeh 3's native mechanism:

- `y_range` is now always increasing: `[-y_pad, h+y_pad]`.
- The array is passed **unflipped**, anchored at `y=[0], dh=[h]`, and the glyph gets
  `origin='top_left'` (`flipud=False`, standard imshow orientation: row 0 at top) or
  `origin='bottom_left'` (`flipud=True`, row 0 at bottom). Both `image` and
  `image_rgba` glyphs accept `origin`.
- Fixed the **swapped padding axes**: `y_pad` was computed from the image *width* and
  `x_pad` from the *height*; now each uses its own axis.
- Moved `im.squeeze()` **before** the range calculation; previously an array shaped
  `(1, H, W)` got correct-shaped squeezed data but a 1-pixel-tall view range.

Verified empirically with a parameter matrix (range direction × data flip × glyph
origin) rendered in headless Chrome: only *increasing range + raw data + origin* puts
the full image in frame with correct orientation. All variants (default, flipud=True,
RGBA, user-supplied figure, two-image grid, colorbar) re-verified after the fix via
screenshots; see `DEBUGGING.md` for the technique.

## Tests

Extended `test_bokeh.py::test_images` (3 shapes × 2 flipud) to assert: y_range is
increasing and covers `[0, h]`; glyph origin is `top_left`/`bottom_left`; source is
anchored at `y=[0], dh=[height]`; the stored array is unflipped (packed uint32 for
RGBA). Full suite: 66 passed in `tests.py`/`test_bokeh.py`/`test_config.py`.

Pre-existing, unrelated: `test_notebook.py::test_demo_notebook_is_current_bokeh_compatible`
fails because the working tree's `demo.ipynb` (uncommitted user edit) uses `%bokehlab`
instead of `%load_ext bokehlab`.
